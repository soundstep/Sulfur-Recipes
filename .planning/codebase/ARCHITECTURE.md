## Pattern Overview

**Overall:** Contract-First Monorepo with OpenAPI Code Generation

**Key Characteristics:**
- `lib/api-spec/openapi.yaml` is the single source of truth for all API contracts
- `lib/api-zod` and `lib/api-client-react` are both generated by Orval from the OpenAPI spec (`lib/api-spec/orval.config.ts`)
- The frontend never writes raw `fetch()` calls — it uses generated React Query hooks from `@workspace/api-client-react`
- The backend validates/types its own responses via the shared `@workspace/api-zod` package
- All packages share workspace dependencies via `pnpm-workspace.yaml` catalog pinning

## Layers

**Shared Contract Layer:**
- Purpose: Define the API contract and generate typed clients/validators
- Location: `lib/api-spec/`, `lib/api-zod/`, `lib/api-client-react/`
- Contains: OpenAPI YAML, Zod schemas, React Query hooks — all generated except the spec itself
- Depends on: Nothing (api-spec is the root); api-zod and api-client-react depend on api-spec
- Used by: Frontend (api-client-react), Backend (api-zod for types)

**Backend Layer:**
- Purpose: Scrape the Sulfur game wiki, cache results, serve via REST
- Location: `artifacts/api-server/src/`
- Contains: Express app, route handlers, wiki parsing logic, in-memory cache
- Depends on: `@workspace/api-zod`, `@workspace/db`, express, pino
- Used by: Frontend (via HTTP)

**Frontend Layer:**
- Purpose: Inventory input, recipe scoring/filtering, crafting chain calculation
- Location: `artifacts/sulfur-recipe-finder/src/`
- Contains: React pages, custom hooks, shadcn/ui components, cyber-themed UI primitives
- Depends on: `@workspace/api-client-react`, Tailwind v4, framer-motion, wouter, React Query
- Used by: End users via browser

**Database Layer (scaffolded):**
- Purpose: Drizzle ORM schema definitions for future persistence
- Location: `lib/db/src/`
- Contains: Schema barrel file (no tables defined yet)
- Depends on: drizzle-orm, drizzle-zod
- Used by: `@workspace/api-server` (dependency declared but schema empty)

## Data Flow

### Primary Request Path — Loading Recipes

1. Browser loads SPA → `artifacts/sulfur-recipe-finder/src/main.tsx`
2. `App.tsx` mounts `QueryClientProvider` and routes to `Home.tsx`
3. `Home.tsx` calls `useRecipesData()` hook (`artifacts/sulfur-recipe-finder/src/hooks/use-recipes.ts`)
4. `useRecipesData` calls generated `useGetRecipes()` from `@workspace/api-client-react`
5. React Query issues `GET /api/recipes`
6. `artifacts/api-server/src/routes/recipes.ts` → checks in-memory cache (TTL: 1 hour)
7. On cache miss: batched fetch from `https://sulfur.wiki.gg/api.php` (10 concurrent requests per batch)
8. Wikitext parsed → `Recipe[]` assembled → cached in module-level variable
9. JSON response returned → React Query caches client-side (staleTime: 5 min)
10. `Home.tsx` runs `buildCraftableSet()` + `scoreRecipe()` on `useMemo` → renders `RecipeCard` list

### Cache Refresh Path

1. User clicks "Force Refresh" button in `Home.tsx`
2. `useRefreshRecipesData().mutate()` issues `POST /api/recipes/refresh`
3. Server clears `cachedData` and `cacheTimestamp` → re-fetches wiki
4. On success: `queryClient.invalidateQueries({ queryKey: getGetRecipesQueryKey() })` triggers re-fetch

### Inventory Scoring Flow (Client-Only)

1. User types/pastes ingredients into textarea → `handleSetIngredients()` builds `Map<string, number>`
2. `buildCraftableSet()` runs iterative fixed-point algorithm: starts from owned items, expands set with craftable recipes
3. `scoreRecipe()` classifies each recipe: `directVariant` (immediately cookable), `chainVariant` (cookable via crafting), `partial` (some ingredients owned)
4. `useMemo` re-runs on `[recipes, activeIngs, catMems]` change
5. Filtered/sorted `ScoredRecipe[]` rendered as `RecipeCard` grid

**State Management:**
- Server state: React Query (`@tanstack/react-query`) via generated hooks
- UI state: React `useState` (local to `Home.tsx`)
- Persistence: `localStorage` key `"sulfur-inventory"` for inventory textarea content

## Key Abstractions

**Recipe:**
- Purpose: A game item that can be crafted, with one or more ingredient variant sets
- Examples: `lib/api-zod/src/generated/types/recipe.ts`
- Pattern: `{ name: string; type: "consumable" | "equipment"; variants: string[][] }`

**ScoredRecipe:**
- Purpose: A `Recipe` decorated with crafting feasibility (direct, chain, partial) based on current inventory
- Examples: `artifacts/sulfur-recipe-finder/src/components/recipe-card.tsx` (type definition)
- Pattern: Extends `Recipe` with `directVariant`, `chainVariant`, `chainSteps`, `haveCount`, `total`, `pct`

**CategoryMembers:**
- Purpose: Maps an ingredient category label (e.g. "any flesh") to specific accepted items (e.g. ["dog flesh", "human flesh"])
- Examples: `artifacts/api-server/src/routes/recipes.ts` — `HARDCODED_CATEGORIES` + wiki parsing
- Pattern: `Record<string, string[]>` passed alongside recipes from API

**Generated API Client:**
- Purpose: Typed React Query hooks matching the OpenAPI spec exactly
- Examples: `lib/api-client-react/src/generated/api.ts`
- Pattern: `useGetRecipes()`, `useRefreshRecipes()`, `getGetRecipesQueryKey()` — never handwritten

## Architectural Constraints

- **Threading:** Single-threaded Node.js event loop for the API server; wiki fetches use `Promise.all` batched at concurrency 10 (`artifacts/api-server/src/routes/recipes.ts:170`)
- **Global state:** Module-level `cachedData` and `cacheTimestamp` variables in `artifacts/api-server/src/routes/recipes.ts:156-158` — shared across all requests, not safe for multi-instance deployments
- **Circular imports:** None detected
- **Code generation:** `lib/api-zod/src/generated/` and `lib/api-client-react/src/generated/` are machine-generated — never edit directly
- **No database:** `lib/db` is scaffolded but has no schema definitions; all data comes from wiki API and is ephemeral

## Anti-Patterns

### Editing Generated Files

**What happens:** Files under `lib/api-zod/src/generated/` or `lib/api-client-react/src/generated/` are modified directly
**Why it's wrong:** Orval regenerates them from `lib/api-spec/openapi.yaml` — all manual changes are overwritten
**Do this instead:** Modify `lib/api-spec/openapi.yaml`, then re-run Orval generation via `lib/api-spec/orval.config.ts`

### Hardcoded Category Members

**What happens:** `HARDCODED_CATEGORIES` in `artifacts/api-server/src/routes/recipes.ts:39-46` maps category names to members statically
**Why it's wrong:** New game items added to the wiki categories won't be reflected automatically
**Do this instead:** Fetch category members from the MediaWiki Category API dynamically when scraping

## Error Handling

**Strategy:** Fail-safe — failed wiki fetches return `null` and are silently skipped; the route returns whatever was successfully fetched

**Patterns:**
- Wiki fetch errors caught per-recipe: `catch { return { recipe: null, ... } }` (`routes/recipes.ts:146`)
- Route-level errors caught and return HTTP 500 with `{ error: string }` JSON
- Frontend shows error state panel when `isError` is true; offers "Retry Connection" button

## Cross-Cutting Concerns

**Logging:** Pino structured JSON logger (`artifacts/api-server/src/lib/logger.ts`) with `pino-http` request serializer; URL query strings stripped from logs
**Validation:** Zod schemas via `@workspace/api-zod` — used for type safety; no runtime request validation middleware on API routes
**Authentication:** None — all API endpoints are public
